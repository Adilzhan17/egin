# EGIN One API

Публичное название — EGIN One. Путь `/api/soilcore` и существующие идентификаторы сохранены для совместимости. Сервер использует Express, SQLite и существующую сессию EGIN. Записывающие запросы требуют `X-EGIN: 1`, браузерные Origin проверяются. Подключение вне localhost требует HTTPS.

## Демонстрация и авторизация

`POST /api/soilcore/demo` создаёт изолированную демонстрационную сессию без регистрации. Оpaque token хранится в HttpOnly/SameSite cookie с путём `/api/soilcore`, сроком 24 часа; сервер хранит только хеш. Этот доступ разрешает только собственные данные симуляции. Просроченные данные удаляются. Для вошедшего пользователя используется его обычная сессия, а состояние сохраняется в профиле.

Реальные устройства, их токены, измерения и история доступны только через сессию владельца. Гостевая демонстрация не создаёт пользователей EGIN и не получает доступа к hardware.

## Чтение и поток

- `GET /snapshot?mode=simulation|hardware&device_id=…` → `{snapshot}`. Без hardware-измерений snapshot равен `null`. `device_id` применяется только к hardware, проверяется владение. Hardware включает `received_at` и `stale`: данные старше пяти часов по времени приёма или измерения считаются устаревшими.
- `GET /history?mode=…&device_id=…&after=seq` → `{items,more}`. Без `after` возвращаются последние 500 записей в порядке времени. С `after` возвращаются следующие 500 по seq. Для hardware курсор ведётся отдельно по каждому устройству.
- `GET /events?mode=…` → `{items}`: до 100 последних событий, каждое имеет `id`, `timestamp` UTC, `virtual_time` для симуляции, `severity`, `code`, `title`, `detail`, `device_id`. События режима и владельца изолированы.
- `WebSocket /ws?mode=…&device_id=…` → `{type:'snapshot',snapshot}`. Проверяются Origin, сессия и владение прибором. Ping/pong и повторная проверка сессии выполняются сервером. Клиент повторяет подключение с задержкой и догружает историю; сам поток не гарантирует воспроизведение пропущенных сообщений.

`source` равен `simulation` или `hardware` и определяется сервером. Отсутствующие данные — `null`, а не ноль. Лабораторные результаты не принимаются за телеметрию. Влажность и pH по умолчанию имеют флаги `MOISTURE_NOT_SOIL_CALIBRATED` и `PH_UNVALIDATED`.

## Управление моделью

`POST /control` принимает `{action,value?}`:

- `play`, `pause`, `reset`;
- `speed` со значением `1`, `60` или `360`;
- `scenario`: `normal`, `rain`, `drought`, `salinity`, `offline`, `low_battery`, `restore`, `sensor_offline`;
- `rainfall`: интенсивность от 0 до 50 мм/ч;
- `checkpoint`, `restore_checkpoint` — сохранение и восстановление модельного состояния в пределах владельца.

Состояние модели и очередь уже декодированных пакетов сохраняются в SQLite. Восстановление контрольной точки начинает новую модельную ветку (`run_id`), не перезаписывает историю и не переиспользует seq. При рестарте сервера сохраняются сценарий, модельное время, пауза, последняя доставка и очередь. Время простоя сервера не моделируется задним числом.

Модель создаёт сырые Modbus-кадры. Постоянный процесс `soilcore_cli` реально проверяет их переносимым C++ ядром. Без бинарника или при ошибке декодера новые измерения не создаются. Путь определяется по стандартным папкам `firmware/soilcore/build` либо `SOILCORE_CLI`. Встроенная очередь CLI — демонстрация ядра; авторитетная очередь симулятора хранится в SQLite, история и её очистка фиксируются одной транзакцией. Это не реализация надёжного транспорта физического прибора.

Сохраняются до 5000 измерений на режим и владельца, до 1000 событий и до 1000 недоставленных модельных пакетов. При переполнении счётчик `radio.lost_packets` растёт. Поддерживается до 64 активных симуляций в процессе; неактивная симуляция выгружается через 10 минут. Для нескольких процессов нужны общие блокировки/координатор симуляций и pub/sub; текущий WebSocket работает внутри одного процесса.

## Реальные устройства

- `GET /devices` возвращает собственные Device ID, названия, последнюю доставку, свежесть и ошибку сенсора.
- `POST /devices` с `{name}` выдаёт `{device_id,token}`. Токен показывается один раз; сервер хранит хеш.
- `DELETE /devices/:id` отзывает токен. История не удаляется.
- `POST /ingest`: `Authorization: Bearer <token>`, `X-EGIN: 1` и JSON с `seq`, `timestamp` UTC ISO 8601 с `Z`, `readings`, необязательными `power`, `radio`, `sensor_error`, `firmware_version`.

`readings` содержит `soil_moisture_pct` (0–100), `soil_temperature_c` (−40…80), `ec_us_cm` (0–20000), `soil_ph` (0–14). Вместо readings можно передать `null` с ошибкой `timeout`, `crc`, `modbus_exception`, `range` или `storage`. `power` может содержать `battery_mv` (0–6000), nullable `battery_soc_est_pct` (0–100, оценка) и nullable `solar_input_mw` (0–10000). `radio` содержит `status` (`connected`/`offline`), `buffered_packets` и необязательный nullable `rssi_dbm`. Сервер не создаёт отсутствующие параметры.

Повтор одинакового пакета с тем же Device ID и seq идемпотентен; другое содержимое с занятым seq даёт HTTP 409. Ограничение истории означает, что дедупликация после удаления старого пакета не гарантируется. `source` и Device ID берутся из токена, а не из пользовательского JSON.

Физические UART/RS485, Wi-Fi/TLS, питание, LoRaWAN и ESP-IDF адаптеры требуют реализации и испытаний. Наличие API и успешный пакет эмулятора не подтверждают работу реального оборудования.
