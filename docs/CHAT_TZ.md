# ТЗ: вкладка «Чат» вместо «Инфо» (Egin / AgriPlan)

## 1. Контекст
Egin — платформа для фермеров Казахстана: карта участков, маркетплейс, услуги, профиль.
Репозиторий: `yedilius/Egin-KZ`, ветка `main`. Прод: фронт `https://egin.perricheno.com`, API `https://egin-api.perricheno.com`.

**Стек**
- Backend: NestJS 11, TypeORM, PostgreSQL+PostGIS, JWT (Bearer или httpOnly-cookie `agro_token`), `class-validator` с `whitelist + forbidNonWhitelisted`, rate limit (`@nestjs/throttler`).
- Frontend: Next.js (static export, `output: "export"`), React, Tailwind, mobile-first, нижняя навигация в `frontend/src/app/page.tsx` (`type ActiveTab = "home"|"map"|"market"|"profile"|"admin"|"info"|"services"`).
- Локально зависимости не ставить; тесты и сборки — в Docker/CI (`docs/TESTING.md`).

**Что уже есть (использовать, не переписывать с нуля)**
- Backend `backend/src/chat/`: сущности `Chat` (типы `direct | regional | global | transaction`, `listingId`, `region/district/village/cropType`, `channelKey`, `isModerated`), `ChatParticipant` (`lastReadAt`), `ChatMessage` (`type`, `body`, `attachmentUrl`, `metadata`).
- Эндпоинты (все под JWT): `POST /chats/direct`, `GET /chats`, `GET /chats/channels`, `GET /chats/:id/messages`, `POST /chats/:id/messages`. Тело сообщения ≤ 1000 символов. Автовступление в региональные каналы.
- Frontend: `frontend/src/components/ui/chat-overlay.tsx` (вынесен в отдельный компонент), `info-center-view.tsx` (заменяемая вкладка).

## 2. Цель
Заменить вкладку **«Инфо»** на **«Чат»**: единое место общения фермеров, покупателей и поставщиков услуг. Просто для пользователя, но с продуманной логикой.

**Принципы:** один экран — один смысл; максимум 2 нажатия до отправки сообщения; ничего лишнего на первом экране; работает на слабом мобильном интернете; тексты на языках приложения (ru/kk/en, как в остальном UI).

## 3. Пользовательские сценарии
1. Открыл «Чат» → видит список диалогов: сверху закреплённые каналы (Мой район, Моя область, Вся страна), ниже личные диалоги по времени последнего сообщения.
2. Из карточки объявления (маркетплейс) или услуги нажал «Написать» → открывается личный диалог с продавцом, в шапке — мини-карточка объявления (`listingId`), диалог не дублируется.
3. Внутри диалога: сообщения по времени, «я» справа, «собеседник» слева, дата-разделители, статус «доставлено/прочитано» (по `lastReadAt`).
4. Непрочитанные: бейдж на иконке вкладки и в списке.
5. Поиск по диалогам и сообщениям (по имени, объявлению, тексту).

## 4. Функциональность
**MVP (обязательно)**
- Список чатов: тип, название (имя собеседника / название канала), последнее сообщение, время, счётчик непрочитанных, пустое состояние с подсказкой.
- Личные диалоги и региональные/общий каналы (использовать существующий API).
- Отправка текста, оптимистичное добавление, повтор при ошибке, защита от двойной отправки.
- Автообновление: polling 5–10 с на открытом чате и 30 с на списке (пауза, когда вкладка не активна); архитектуру закладывать так, чтобы позже заменить на WebSocket/SSE без переписывания UI.
- Прочитано/непрочитано (`PATCH /chats/:id/read` — новый эндпоинт, обновляет `lastReadAt`).
- Быстрые шаблоны для сделок в диалоге по объявлению («Ещё актуально?», «Какая цена за партию?», «Можно доставку?»).
- Вложение-карточка объявления/участка через `metadata` (`type: "listing"`), без загрузки файлов.
- Жалоба на сообщение и блокировка пользователя (минимум: скрыть диалог локально + `POST /chats/:id/report`).

**Этап 2 (не делать в первом PR)**
- WebSocket/SSE-уведомления, push, фото, голосовые, реакции, ответы на сообщения, закреп, модерация каналов (`isModerated`), перевод сообщений.

## 5. API (что добавить/изменить)
| Метод | Путь | Назначение |
|---|---|---|
| GET | `/chats/unread-count` | сумма непрочитанных для бейджа |
| PATCH | `/chats/:id/read` | отметить прочитанным |
| GET | `/chats/:id/messages?before=<iso>&limit=30` | пагинация (курсор по времени), сейчас отдаётся всё |
| POST | `/chats/:id/report` | жалоба `{messageId?, reason}` |
| GET | `/chats?search=` | поиск по диалогам |

Правила: только участники читают и пишут (`403` иначе); нельзя писать самому себе; валидация DTO; лимит частоты на отправку (например 30 сообщений/мин); в ответах не отдавать `passwordHash` и телефоны собеседников без необходимости (для личных чатов — только `fullName`, роль, регион).

## 6. Данные
Миграции — в `backend/src/database/migrations/` (только новые файлы, существующие не менять). Индексы: `chat_messages(chatId, createdAt DESC)`, `chat_participants(userId)`. Таблица жалоб `chat_reports(id, chatId, messageId, reporterId, reason, createdAt)`.

## 7. Frontend
- В `page.tsx` заменить таб `info` на `chat` (иконка, подпись, бейдж). `InfoCenterView` **не удалять** — перенести доступ к новостям в раздел «Главная» (блок новостей там уже есть) или в меню профиля.
- Компоненты: `ChatTab` (список) + `ChatThread` (диалог) на базе существующего `chat-overlay.tsx`; хуки `useChats`, `useThread` (polling, отмена запросов, обработка 401 через существующий `handleUnauthorized`).
- Токен брать так же, как в остальном коде (`localStorage.agro_token` + `credentials: "include"`), URL — через `apiUrl()` из `@/lib/api`.
- UX: минимальный размер текста 12 px, зоны нажатия ≥ 44 px, safe-area на iOS, автопрокрутка вниз только если пользователь у низа, клавиатура не перекрывает поле ввода, скелетоны загрузки, понятные ошибки.

## 8. Безопасность и производительность
- Экранирование вывода (никакого `dangerouslySetInnerHTML`), ссылки в сообщениях — `rel="noopener noreferrer"`.
- Все проверки доступа на сервере, не на клиенте. Не доверять `senderId` из тела.
- Пагинация обязательна; список чатов — один запрос без N+1.
- Не увеличивать rate limit; отправка не должна ломать лимиты `/auth/*`.

## 9. Тесты (обязательны)

## 10. Критерии приёмки
- Вкладка «Чат» вместо «Инфо», бейдж непрочитанных работает.
- Можно написать продавцу из объявления и получить ответ на другом аккаунте; диалог не дублируется.
- Чужой чат недоступен (403/404), проверено тестами.
- CI (`.github/workflows/ci-cd.yml`) зелёный: backend, e2e, frontend, docker.
- Нет регрессий в других вкладках; нет новых секретов в коде.

## 11. Ограничения для исполнителя
